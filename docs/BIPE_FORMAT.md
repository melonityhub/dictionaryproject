# فرمت `.bipe` و مدل ترجمه‌ی آفلاین (بسته‌ی گوگل / ML Kit)

> همه‌ی موارد زیر از **مهندسی معکوس فایل‌های همین بسته** به‌دست آمده؛ مستندات رسمی وجود ندارد.
> هرجا «احتمالاً» آمده یعنی از روی شکل داده‌ها حدس زده شده، نه تأییدشده.

## ۱. `.bipe` چیست؟
یک **FlatBuffer** با شناسه‌ی فایل `BIPE` (بایت‌های ۴ تا ۷). محتوا:

| بخش | توضیح |
|---|---|
| نام | مثل `encoder_swizzled_birnn_0` |
| Program → engine | رشته‌های `tflite` / `generic` |
| Segment.inputs / outputs | نام کوتاه ⇄ نام تنسور در گراف (مثل `src_enc` ⇄ `embedded_base_inference/decoder/beam_search_init/feed_src_enc`) |
| Segment.`tflite_flatbuffer` | یک مدل **TensorFlow Lite کامل ولی بدون وزن** (با توضیح «TOCO Converted.») |
| Program.blobs | آرایه‌های بایتی وزن‌ها (ماتریس‌های کوانتایزشده‌ی uint8، بایاس‌های int32، جدول embedding) |
| Segment.map | جدول `(شماره‌ی بلوب، شماره‌ی تنسور TFLite)` — هر وزن در بافر کدام تنسور می‌نشیند |

برای ساخت مدل قابل‌اجرا باید بلوب‌ها طبق جدول نگاشت داخل بافر تنسورها گذاشته شوند (`bipe.build_tflite`).
صحت: اندازه‌ی هر بلوب دقیقاً برابر `حاصل‌ضرب شکل × اندازه‌ی نوع` تنسور مقصد است (مثلاً ۱۹۲×۱۹۲=۳۶۸۶۴).

## ۲. اجزای مدل (به‌ترتیب اجرا)
| فایل | نقش | شکل‌ها |
|---|---|---|
| `encoder_embed_ids_0` | embedding توکن مبدأ | ids `[1,4]` int32 → `[1,4,192]` uint8 ؛ جدول ۶۰۰۰×۱۹۲ |
| `encoder_swizzled_birnn_0` | لایه‌ی ۱ BiLSTM (یک گام زمانی، fwd+bak) | ورودی ۱۹۲ ، حالت‌ها `[4,192]` (c: int16 ، m: uint8) |
| `encoder_swizzled_birnn_1` | لایه‌ی ۲ BiLSTM | ورودی ۳۸۴ = الحاق خروجی fwd/bak لایه‌ی قبل |
| `encoder_swizzled_birnn_2` | پروژکشن نهایی + tanh | ۳۸۴ → ۱۹۲ ⇒ `src_enc [72,4,192]` |
| `decoder_init_0` | آماده‌سازی attention | `source_contexts/source_vecs` |
| `decoder_step_embed_ids_0` | embedding توکن قبلی مقصد | ids `[8,1]` → `[8,192]` ؛ جدول ۴۰۰۰×۱۹۲ |
| `decoder_step_0` | یک گام دیکودر (LSTM دولایه + attention) | خروجی `log_probs [8,4000]` |

- طول منبع ثابت **۷۲** توکن، `batch=4`، **۸ فرضیه** (hypothesis) — هر سه از شکل تنسورها.
- همه‌ی فعال‌سازی‌ها uint8 با `zero_point=128`, `scale=1/128`؛ حالت سلول LSTM به‌صورت int16 (`scale=2^-15`)؛
  `log_probs` uint8 با `scale=0.0625`, `zero_point=255` (یعنی لگاریتم‌ها در بازه‌ی [−۱۶، ۰] **ساتوره** می‌شوند).
- پدینگ: uint8 با `scale=1/255` ⇒ مقدار ۲۵۵ یعنی «پد».
- بین مدل‌ها بایت‌های خام (بدون dequantize) رد و بدل می‌شود چون scale/zero-point مدل‌ها با هم جور است.
- beam search و تبدیل متن⇄توکن **بیرون از مدل** است و در این پروژه بازسازی شده (`nmt.py`, `textproc.py`).

## ۳. پیش‌پردازش (از `processor_spec.pb`)
فقط *نام* پردازنده‌ها در فایل هست: `upp_offline`, `b2a:mode=tokenize`, `lc`. کد آن‌ها داخل کتابخانه‌ی بومی است؛
بازسازی این پروژه بر پایه‌ی واژگان (`resources/*.vocab`) است:
علائم نگارشی در vocab به‌صورت واژه‌ی جدا (`▁.` `▁,` `▁?`) هست ⇒ tokenize؛ ارقام فقط ASCII و نیم‌فاصله/؟ ، ؛ در vocab نیست
⇒ ارقام/علائم فارسی ASCII و نیم‌فاصله→فاصله. توکنایز: unigram (Viterbi) با امتیاز=ln(احتمال) از ستون دوم `.vocab`
(فایل‌های `.model` هیچ piece ای ندارند و فقط تنظیمات‌اند).

## ۴. چیزهایی که نمی‌توان از فایل‌ها فهمید
- مقدار/معنای دقیق اعداد داخل `translation_model.pb` (مثل ۳٫۰ و ۵٫۰ و ۴ و ۲) — نام فیلدها در پروتو منتشر نشده.
- پارامترهای beam search و جریمه‌ی طول در ML Kit؛ این‌جا beam پیش‌فرض ۴ و نرمال‌سازی طول به‌سبک GNMT (α=۰٫۶) است.
  خروجی ممکن است در برخی جمله‌ها با خود ML Kit **کمی** فرق کند.
